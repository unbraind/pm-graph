# Release runtime stamping audit

Audit date: 2026-11-15. Scope: all 33 rollout PRs plus the pm-jira pilot. The separate pm-ops self-release workflow was also checked. No review threads, merges, releases or CI v2/pin branches were changed.

The released shared workflow at `7687a35d7522482bd8361d60dbc2589e9afbc81c` updates package/lock metadata and `manifest.json`, then calls `stampExtensionVersion` on `index.ts`, `src/index.ts` and `src/extension.ts`. The helper recognizes literal properties inside direct `defineExtension({...})` calls. There is no configurable stamp-target input. `prepare-script` runs after stamping and before the clean build.

Three callers need package preparation: plain-object default exports in pm-context and pm-csv, and pm-graph’s `EXTENSION_VERSION` constant. The fix uses the existing released hook; no shared-workflow change or new pm-ops release is required.

Actual package names are the unscoped npm names declared in package.json. Registry tarballs were downloaded and read without running lifecycle scripts. All downloadable latest tarballs have matching package, manifest and runtime versions. HTTP 404 is recorded as unavailable/unpublished, not a passing parity check.

## Reproduction and limits

In each affected package, `node --test test/release-runtime-version.test.ts test/release-workflow.test.ts` builds an isolated copy at `2099.1.2-3` after running the released shared stamper and the hook selected by the actual caller YAML. pm-csv and pm-context import the built default export; pm-graph activates the built export through the public SDK harness and checks the ping command result. Package and manifest are asserted separately. Preparation is idempotent and refuses inconsistent metadata, missing targets and ambiguous targets before editing source.

Revert proof: remove only `prepare-script: release:prepare` from the caller, run `node --test --test-name-pattern="scratch release build" test/release-runtime-version.test.ts`, and restore the caller. All three fail specifically on the stale built runtime assertion. The package source, metadata and existing dist are never bumped by this scratch test.

At inspected pm-graph main `f951fed926899b932966fc0bd9adb954a213ff22`, package/manifest are `2026.11.15` while the source constant and built command still report `2026.11.12`. Registry latest was `2026.11.12`, with matching runtime; a direct lookup of `pm-graph@2026.11.15` returned E404; this is evidence of stale release metadata on main, not evidence that an npm release with a stale version has shipped. This PR also restores current source/dist parity to `2026.11.15`. A pre-existing prepared release artifact is outside this caller fix and must be rebuilt before any future publication if it contains the old constant.
